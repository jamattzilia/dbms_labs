# Laboratory Work No. 4

**Subject:** Creating a simple database in Microsoft Access 2010. Entering and sorting records.
(Practical work 2: Creating a database consisting of two tables. Practical work 3: Creating a query to the final database.)

**Objective:**
- learn how to create a table with the help of templates and the Table Designer;
- ensure correct data entry into a table;
- learn how to sort records in a table;
- design a two-table database with a one-to-many relationship and cascade update/delete;
- learn how to build simple and complex selection queries.

**Variant:** this laboratory work has no variants — the task, sample tables and their data are the same for every student.

## A note on the environment

This lab is written around the Microsoft Access 2010 desktop GUI (ribbon menus, the Table Designer, the relationship diagram editor, the Query Builder), which is not available in this Linux environment. To make the work reproducible and verifiable rather than just a transcription of the instructions, every table, relationship and query below was rebuilt as an equivalent **SQLite** database and plain **SQL**, which is the exact operation Access performs behind its GUI (Access tables *are* relational tables, an Access "data scheme" relationship with cascade options *is* a `FOREIGN KEY ... ON UPDATE/DELETE CASCADE`, and the Query Builder's "select query" *is* a `SELECT` statement). All data and results below were generated by actually running these scripts, not typed by hand.

## Practical work 2. Creating a database consisting of two tables

### Tasks 1–3. "Training facilities" database, tables "Groups" and "List"

GUI steps: create a new blank database **Training facilities** → **Create ▸ Table Designer** → build **Groups** with fields `Study group` (Number, set as the key field) and `Teacher` (Text) → save as "Groups" → build **List** with fields `Code` (Number, key field), `Last name`, `First name`, `Patronymic` (Text), `Year of birth`, `School`, `Class` (Number), `Study Group` (Number; on the *Lookup* tab set control type = combo box, row source = Groups, so the field is filled by picking a group from a dropdown) → save as "List".

SQL equivalent: [`sql/03_training_facilities_schema.sql`](sql/03_training_facilities_schema.sql). The Access "Lookup" combo box on `List.StudyGroup` is the everyday UI for picking a value that a foreign key constrains; the constraint itself is `FOREIGN KEY (StudyGroup) REFERENCES Groups (StudyGroup)`.

### Task 4. Data scheme (relationship)

GUI steps: **Database Tools ▸ Relationships** → add both tables → drag `Groups.Study Group` onto `List.Study Group` → in the Edit Relationships dialog, tick *Enforce Referential Integrity*, *Cascade Update Related Fields* and *Cascade Delete Related Records* → Create. Access draws a "one" (`Groups`) to "many" (`List`) connector.

SQL equivalent: the same foreign key declared above with `ON UPDATE CASCADE ON DELETE CASCADE`.

### Task 8. Verifying cascade delete

GUI steps: in `Groups`, select the first row (group 201) → right-click ▸ *Delete Record* → confirm → open `List` and confirm every row that referenced group 201 is gone.

SQL equivalent run: `DELETE FROM Groups WHERE StudyGroup = 201;`.

Verified result — both rows that referenced group 201 (Чернова, Архипов) were removed from `List` automatically:

```
Groups (final): (202, Вильданова Р.Ш.) (203, Зайцева С.А.) (204, Зазулина З.А.) (205, Друк Н.Н.)
List (final):   Куликов -> 203   Баранкова -> 204   Новоселов -> 205
```

This is the state saved in **`training_facilities.db`** — the state to be presented to the teacher (`Groups` table, `List` table, `List` form), per the assignment.

## Practical work 3. Creating a query to the final database

Works against `employees.db` (the `Employee` and `Student` tables from Practical work 1).

### Task 2. Select queries via the Query Builder

GUI steps ("phone book" query): **Create ▸ Query Design** → add the `Student` table → double-click the fields to include → in the `Last Name` column's *Criteria* row type `Like "С*"` → **Save**, name it "phone book" → **Run**.

SQL equivalent and verified result:

```sql
SELECT CodeStudent, LastName, FirstName, Patronymic, PhoneNumber
FROM Student
WHERE LastName LIKE 'С%';
```
→ Соколова, Сорина (both last names start with С).

GUI steps ("Address" query): same as above, but in the `Address` column's *Criteria* row enter a condition that matches "Москва" or "Люберцы" → save as "Address" → Run.

SQL equivalent and verified result:

```sql
SELECT CodeStudent, LastName, FirstName, Address
FROM Student
WHERE Address LIKE '%Москва%' OR Address LIKE '%Люберцы%';
```
→ Петров, Гаврелеева, Мухина, Апареева, Глинкина, Сорина.

### Separate task (four extra queries)

All four are built the same way in the Query Builder — add a table, pick the fields, add a *Criteria* condition on the relevant column, save and run. SQL equivalents and verified results (all in [`sql/06_queries.sql`](sql/06_queries.sql)):

1. **Students named Olga:**
   ```sql
   SELECT CodeStudent, LastName, FirstName, Patronymic FROM Student WHERE FirstName = 'Ольга';
   ```
   → Гаврелеева Ольга Ивановна, Сорина Ольга Сергеевна.

2. **Employees whose organization starts with "Р"** (the assignment's Latin "P" is the visually identical Cyrillic Р in the sample data — `Employee` has no person name starting with Р, but two organizations do):
   ```sql
   SELECT Code, Organization, LastName, FirstName FROM Employee WHERE Organization LIKE 'Р%';
   ```
   → Растр (Иванов), Рубин (Сергеева).

3. **Students trained as "технолог" (technologist):**
   ```sql
   SELECT CodeStudent, LastName, FirstName, Specialty FROM Student WHERE Specialty = 'технолог';
   ```
   → Иванов, Петров, Мухина, Апареева, Глинкина.

4. **Employees working as engineer or accountant:**
   ```sql
   SELECT Code, Organization, LastName, FirstName, Position FROM Employee WHERE Position IN ('инженер', 'бухгалтер');
   ```
   → Иванов (инженер), Никитина (бухгалтер).

## Conclusion

This laboratory work covered building Access-style relational databases end to end: creating a table from an application-part template, creating a table by hand with the Table Designer (including autonumber/counter keys), entering and sorting records, designing a two-table schema with a one-to-many relationship enforced by referential integrity and cascading updates/deletes, and building selection queries with text and set-membership criteria. Since the Access GUI itself was not available in this environment, every step was additionally reproduced and verified as an equivalent, runnable SQLite database and SQL script — the same relational operations Access performs under its ribbon menus.
